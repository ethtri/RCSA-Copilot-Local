Make the AI’s work visible.

The current demo is more careful and defensible than v3. Its best AI features are harder to discover, and too much of the main experience explains the work instead of helping users complete it.

All four concerns are supported by the review. Keep the strong evidence handling and restrained visual identity. Focus the next revision on useful AI proposals, realistic choices, simpler language, and reliable interactions.

1. Why v3 feels more capable

The older version more visibly offered to do the next task: add a risk, propose a score, link a control, or draft a response for the selected strategy. The current version often offers analysis to read, followed by a conventional form. That difference changes the impression of capability even where the current implementation is stronger.

The comparison uses the preserved portal demo in the v3 repository at commit 47e662e. The repository’s root README now describes a later scaffold, so the archived portal experience is the relevant comparison.

Do not restore v3’s apparent precision. Its confidence and match percentages are authored demo values, and its residual-risk calculation is simplistic. The useful lesson is the range of actions. The current distinction between a proposed control, implementation, testing and current risk is considerably more credible.

Make the AI contribution concrete

Lead with a prepared change, showing what AI found and what it proposes. For example:

Suggested assessment update · 2 sources

Urgent payments have not been tested.

The September test covers the old procedure. Review the suggested rating explanation and testing plan.

Review suggested update   ·   Why?   ·   View sources

That action should open an exact before/after comparison. Let the owner apply the rationale without accepting the proposed score, edit individual fields, or keep the existing conclusion. Record what was accepted. This follows the human-AI design principle that people should be able to correct and refine AI output. Microsoft HAX guidance.

Risk discovery is a valuable next capability, but needs a complete lifecycle: source, cause/event/harm, draft status, assessment requirements, review and report inclusion. A new polished card without those consequences would recreate the realism problem.

2. Make this behave like a product

A demo can use synthetic data and scripted assistance while still being believable. It needs consistent inputs, editable outputs, state changes, alternate paths and recovery. It does not need a production backend to demonstrate those behaviors.

Confirmed behavior gaps

  1. The reviewer has to follow the story. After submission, the only decision path is Send challenge. The model rejects review completion until a reply exists. Let a reviewer agree directly, ask a question, or return the assessment, each with an appropriate reason.
  2. The response draft ignores the selected approach. I selected Request acceptance and opened Review AI draft. It proposed Strengthen controls. Using it changed the selected radio option to Strengthen controls. If AI recommends a different approach, present that as an explicit recommendation with a clear switch action.
  3. Reply help is tied to wording. “Who is responsible for the testing action?” produced no AI suggestion. The source supports the narrow alternative “Who owns the testing action?” Buildable assistance should recognize that shared intent and answer from the recorded owner. Keep an honest fallback for questions the available records cannot answer.
  4. A report draft has no editor. The screen labels the summary AI-assisted and asks for confirmation, but supplies no editing path. Add Edit summary, Restore suggested summary and Confirm summary. The report also focuses on one risk; View all 3 risks leads back to the assessment rather than producing a complete report.

Operational boundaries to clarify

Open/Inspect action leads to the response workspace, where the action remains Open and evidence describes what is required. This is an action plan, not an execution record. Either call it View action plan or show the minimal execution record: status, accountable owner, due date, submitted evidence and closure decision.

The management decision is correctly shown as pending, but its owner, forum and date are fixed, with no routing or recorded decision. Keep this boundary explicit. A decision-request record is enough for the demo if actual management approval is outside scope.

Adding a proposed control increases the count under Current controls. Separate 2 current · 1 proposed; do not make users open the detail to discover that the new protection does not yet exist.

The GRC failure after adding that control is a useful strength: completing review correctly paused sync because the new control lacked a GRC identifier. The app preserved the assessment and identified the administrator’s next responsibility. Improve it by naming the affected control and surfacing the missing mapping before submission. That demonstrates a credible integration boundary.

A credible implementation contract

For each AI action, show the relevant records and versions, the proposed structured change, the human application step, and the resulting saved version. A real implementation could retrieve permitted evidence, generate typed proposals, validate references and required fields, apply owner-approved changes, and queue reviewed updates to GRC. Ratings and approvals remain governed by the institution’s method and roles. The UI should make this chain visible without exposing implementation machinery.

4. What would make it feel premium

Keep the palette and overall restraint. The green, pale surfaces and fine borders already form a recognizable visual system. Premium quality now depends on hierarchy, readable controls, trustworthy state and smooth interaction.

Make room for the task

The assessment uses a global header, sync status, process context, step navigation, large title and introduction before the form. Analysis adds a back row, risk selector, another large heading, lens explanation and more tabs. Roughly half the first desktop viewport can disappear before substantive work starts. Rationale editors then show only a few lines, with an internal scrollbar.

Use a compact assessment header with process, period, risk, status and step. Try functional titles around 28–32px. Keep the rating editor beside one concise AI finding; open detailed analysis without losing the assessment context. Give rationale fields five to seven visible lines or auto expansion.

Improve the controls users depend on

  • Validation: I cleared Control name and selected Add proposed control. No inline error appeared, focus stayed on the action, and the error toast was blurred behind the modal. The empty field was above the visible scroll position. Show the exact error inside the editor, preserve it, link it to the field and focus the first invalid field. W3C form feedback guidance.
  • Focus: Suggest controls rebuilt the page and left focus on BODY. Preserve the selected control during local changes. Reserve heading focus and page-top scrolling for actual navigation.
  • Readability: dashboard metadata often uses 9–12px text while headings use 30–50px. Increase operational content toward 14px and secondary metadata toward 12–13px. Several small muted CSS colors calculate below 4.5:1 on white; check their final rendered pairs.
  • Editors: source excerpts, definitions, full control designs and multi-task plans share one narrow dialog. Use a consistent source drawer and a wider editor for substantial work. Keep a stable header/action footer and one scroll region.
  • Save state: distinguish Draft saved in this session, Not yet recorded, Recorded version 2, and GRC sync state. If session storage fails, show the loss-of-persistence state once.
  • Responsive: at measured CSS width 640px the header produced page overflow, a wrapped quarter and clipped avatar. At 390px the reviewed screen reflowed without horizontal overflow, but header/context still consumed roughly 300px. Collapse the header earlier and reduce narrow-screen chrome.

Add sleek motion with a purpose

My suggested starting values are 140–180ms for local panel changes, 180–220ms for drawer entry/exit, and a brief fading highlight on fields changed by an accepted AI draft. Keep actions immediately usable. Preserve reduced-motion support. Use genuine progress feedback for work that is pending; avoid an artificial thinking delay in a local scripted demo.

Motion should help people understand what changed and where the result went. That functional approach is consistent with Fluent 2 motion guidance. The timing values above are design recommendations for this app, not measured defects or a required standard.

Screen-by-screen evidence

Fresh screenshots were captured during this review and opened for inspection. Expand any step to see the screen. Full-page captures can repeat or reposition sticky elements; the notes distinguish visual evidence from interaction and source checks.

1. Dashboard — a strong identity, but small operational text

The AI briefing is prominent and the work queue gives a believable entry point. Keep these. The headline and heatmap dominate while dates, status details and source metadata are small.

2. Changes — useful context repeated across large blocks

The dated procedure change, near miss and test limit are useful. Turn them into an AI-prepared update with inspectable supporting evidence. The full-page summary and later analysis repeat much of the same story.

3. Rating and analysis — rigorous, but mainly reading and form filling

The rating fields are editable and definitions are available. AI analysis separates observed facts from interpretation, but ends with advice rather than a proposed update. Keep the rigor in a side panel and connect it to a reviewable change.

4. Investigation — a current strength to keep

The timeline joins records while acknowledging an uncertain link. Confirm, Keep provisional and Dismiss make the judgment concrete. Make this accessible from the main finding without a heavy navigation detour.

5. Controls and plans — the best AI capability is buried

Default Controls places AI improvement behind a disclosure near the bottom. Opening it and choosing Suggest controls reveals existing/enhance/new choices. The generated control design and plan are editable and preserve the distinction between proposed work and current protection.

6. Error recovery — the message is behind the dialog

Clearing Control name and selecting Add proposed control kept the dialog open, but did not identify the missing field. The toast appeared behind the backdrop. DOM inspection found zero aria-invalid fields and focus still on Add proposed control.

7. Response and review — choices do not fully govern behavior

After selecting Request acceptance, the AI proposed Strengthen controls. The reviewer’s initial screen offered a question but no agree-and-complete path. A plain ownership question then disabled reply assistance.

8. Report and sync — credible limits, incomplete final artifact

The review completed after a manual reply, preserving the open testing action and pending management decision. Sync paused for an unmapped proposed control. The report accurately shows those limits, but its summary has no editor and its top-level view covers one risk.

A focused next revision

Make one complete, impressive journey work well before expanding the number of analysis screens.

  1. AI prepares the refresh: show the evidence change, affected risk, proposed rationale/rating and missing evidence.
  2. The owner reviews changes: inspect sources, edit or keep individual proposals, and apply them explicitly.
  3. AI proposes a control improvement: edit the design, distinguish current and proposed protection, then generate a retained task plan.
  4. The response follows the chosen approach: draft mitigation, acceptance request, activity change or transfer as appropriate; explain any suggested change of approach.
  5. Review supports real choices: agree directly, ask a natural question, or return for changes. Preserve each version.
  6. The report is useful: cover all risks, allow summary edits, expose open work and pending decisions, and show the reviewed version’s sync status.

Acceptance checks for that revision

  • A first-time viewer encounters a useful AI proposal during the primary flow.
  • Applying a proposal shows exactly what changed and allows correction; it does not silently lower confirmed risk.
  • Each response approach produces relevant content, or a clear reason it cannot be drafted.
  • Equivalent ownership/test-scope questions return equivalent recorded facts; unsupported questions get a useful fallback.
  • An adequate assessment can complete review without an invented question.
  • Report text can be edited and confirmed; changed underlying records require renewed confirmation.
  • Missing fields show specific persistent errors inside the open editor. Local updates preserve keyboard focus.
  • Work labels lead to the promised object; proposed controls and planned work remain clearly marked.
  • 390, 640, 768, 1024 and 1440px layouts and enlarged text are checked, including long labels and errors.
  • Short transitions explain state changes; reduced motion remains supported.
